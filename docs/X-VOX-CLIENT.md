# `X-Vox-Client` 헤더 명세 v1

vox.ai 클라이언트 SDK 6종이 공유하는 계보 선언 계약이다. javascript · react ·
react-native · flutter · python · cli 가 모두 이 문서와
[`conformance/x-vox-client.vectors.json`](../conformance/x-vox-client.vectors.json)
을 따른다.

## 목적

클라이언트가 **어떤 vox.ai SDK 레이어로 빌드됐는지**를 전송 계층에서 선언한다.

계보는 콜의 속성이 아니라 빌드의 속성이다. 그래서 per-call 옵션으로 두지 않는다.
앱 개발자가 호출할 때마다 값을 정할 수 있으면 그 값은 계보가 아니라 입력이고,
입력은 틀릴 수 있다. 2026-07-28 사고가 정확히 그랬다. 고객이 공개 옵션
`sourceType: "web"` 을 넣자 서버 allowlist 밖으로 나가 `create_call` 이 죽었다.

## 헤더 문법

```abnf
X-Vox-Client = layer *( SP layer )
layer        = name "/" version
name         = 1*32 ( %x61-7A / %x30-39 / "-" )          ; [a-z0-9-]
version      = 1*32 ( ALPHA / DIGIT / "." / "-" / "+" )  ; [A-Za-z0-9.+-]
SP           = %x20
```

```
X-Vox-Client: react-sdk/1.2.0 js-sdk/0.3.0
```

- 구분자는 공백 1개. 값의 앞뒤에 공백을 두지 않는다.
- `name` 은 소문자만 허용한다. 대문자 · 언더스코어 · 비 ASCII 는 문법 위반이다.
- 보낼 레이어가 없으면 **헤더 자체를 보내지 않는다.** 빈 값을 보내지 않는다.

## 레이어 순서

**바깥 레이어부터**, 즉 앱에 가까운 순서로 나열한다.

등록은 반대로 안쪽부터 일어난다. ESM 은 의존 모듈을 먼저 평가하므로 core 가
자기 자신을 먼저 등록하고 wrapper 가 그 다음에 등록한다. 헤더는 **등록 역순**
으로 직렬화한다.

레이어가 하나뿐인 구현에서는 역순이 무의미하지만 규칙은 동일하다.

## 의미 — "로드된 레이어"이지 "호출 경로"가 아니다

등록은 모듈 로드 시점에 일어난다. 따라서 이 헤더는 **그 빌드에 어떤 레이어가
적재돼 있는지**를 말할 뿐, 이 콜이 실제로 그 레이어를 통과했다는 보장이 아니다.
앱이 react wrapper 와 core 를 둘 다 import 하고 core 를 직접 호출해도 헤더에는
두 레이어가 다 실린다.

서버는 이 값을 라우팅이나 권한 판정에 쓰지 않는다. 위조 가능한 값이기 때문이다.
태깅 전용이다.

## 중복 처리

같은 `name` 이 두 번 등록되면 **먼저 등록된 것만 남기고 이후는 버린다.** 버전이
달라도 마찬가지다.

등록은 idempotent 하다. HMR · 중복 번들 · 모듈 재평가로 같은 등록이 반복돼도
목록이 자라지 않는다.

## 인스턴스 중복

registry 는 **모듈 스코프**다. `globalThis` 를 쓰지 않는다.

core 복사본이 둘 번들되면 registry 도 둘이다. wrapper 는 자기가 import 한 복사본에
등록하고 같은 복사본의 `Conversation` 을 쓰므로, 각 헤더는 실제 사용된 코드의
버전을 정확히 말한다.

`globalThis` 공유 registry 를 쓰면 먼저 로드된 복사본의 버전이 다른 복사본의 콜에
실려 **거짓이 된다.** 중복 제거보다 정확성을 택한다.

## 상한

| 항목 | 값 |
|---|---|
| 최대 레이어 수 | 8 |
| 헤더 값 최대 길이 | 256 바이트 |

초과하면 **앞에서부터**, 즉 바깥 레이어부터 버린다.

바깥이 아니라 안쪽을 버리면 우리 core 가 사라진다. 넘치는 상황은 앱이 자기
레이어를 여러 개 등록했을 때인데, 그때 보존해야 할 것은 장애 귀속에 쓰이는 우리
SDK 레이어다.

그래서 **헤더는 전체 계보를 보장하지 않는다.** 상한 안에서의 best-effort 다. 공식
wrapper 라도 앱이 레이어를 많이 등록하면 헤더에서 빠질 수 있다. 다만 그때도 body 의
`source_type` 은 영향받지 않는다.

## malformed 처리 — fail-open

- 문법을 어기는 레이어는 **조용히 버린다.** 정규화하거나 치환하지 않는다.
  치환은 거짓을 만들고, 폐기는 알려진 부재를 만든다.
- 입력을 trim 하지 않는다. 공백이 섞였으면 문법 위반이므로 버린다. 레이어 값은
  빌드 상수이지 사용자 입력이 아니므로 관대할 이유가 없다.
- 등록 함수는 **절대 throw 하지 않는다.**
- 남은 레이어가 0 이면 헤더를 보내지 않는다.
- **어떤 경우에도 계보 때문에 콜이 실패하지 않는다.**

## body 와의 관계

이 헤더는 기존 body 필드를 대체하지 않는다.

`source_type` · `version` · `metadata.runtime_context.source` 는 **그대로
유지한다.** 서버가 헤더를 읽기 시작하는 것은 PROD-2196 이고, 그 전까지 body 가
유일한 계보 경로다.

body `source_type` 의 **값도 바꾸지 않는다.** agent-server 의
`dynamic_variable_service` 가 이 문자열로 동작을 가르므로, 값이 바뀌면 dynamic
variables 동작이 함께 바뀐다. 헤더는 진실을 새로 싣는 자리이고, body 는 기존
동작을 유지하는 자리다.

### 헤더와 body 는 서로 다른 규칙을 따른다

이 둘을 같은 규칙으로 묶으면 안 된다. 성격이 다르기 때문이다.

|  | 헤더 | body `source_type` |
|---|---|---|
| 무엇인가 | 공개 태깅 정보 | legacy 서버 라우팅 키 |
| 담기는 것 | **상한 적용 후 남은** 유효한 레이어 | 인정된 SDK 이름 **하나** |
| 인정 목록 밖 레이어 | 실린다 | **영향을 주지 않는다** |
| 상한 | 적용된다 | **적용되지 않는다** |

- body 값은 인정된 SDK 이름 집합 안에서만 고른다. JavaScript core 기준
  `js-sdk` · `react-sdk` · `react-native-sdk` 이며, 그중 **가장 바깥**을 쓴다.
  하나도 없으면 `js-sdk` 로 폴백한다.
- **헤더의 첫 레이어와 body 의 `source_type` 은 다를 수 있다.** 앱이 자기
  레이어를 등록하면 헤더 첫 자리는 그 앱 레이어이지만 body 는 바뀌지 않는다.
- body 선택은 **개수 · 길이 상한을 적용하기 전** 목록에서 한다. 그러지 않으면
  앱이 레이어를 여러 개 등록한 것만으로 wrapper 가 상한에 밀려 body 가 조용히
  바뀐다. body 정체가 헤더 길이 제한에 좌우되면 안 된다.

### 인정 목록과 새 wrapper

새 공식 wrapper 를 추가하면 **core 의 인정 목록도 함께 갱신해야 한다.** 빠뜨리면
그 wrapper 는 body 선택에서 건너뛰어지고 **그 다음으로 바깥에 있는 인정된 이름**이
대신 선택된다. 인정된 이름이 하나도 없을 때만 `js-sdk` 로 폴백한다. 즉
`vue-sdk → react-sdk → js-sdk` 로 쌓이면 body 는 `js-sdk` 가 아니라 `react-sdk` 다.

이 폴백이 조용한 것은 의도된 선택이다. agent-server 의 분기 조건이
`"sdk" in source_type` 이라 `js-sdk` · `react-sdk` · `react-native-sdk` 가 **모두
같은 분기를 탄다.** 즉 목록 누락은 동작을 바꾸지 않고 관측 라벨만 덜 정확하게
만든다. 그리고 정확한 계보는 이제 헤더가 싣는다.

서버 분기가 wrapper 별로 갈라지는 날이 오면 이 전제가 깨진다. 그때는 폴백을
조용히 두지 말고 wrapper 통합 테스트에서 실패시켜야 한다.

### 위조는 막지 못한다

`registerClientLayer` 는 공개 API 이므로 앱이 `react-sdk` 를 사칭해 body 값을
바꿀 수 있다. 브라우저 번들에서 import 가능한 함수는 호출도 가능하므로 이건 구조적으로
막을 수 없다.

막을 수 있는 것은 **영향의 크기**다. 인정 목록 덕분에 사칭 가능한 값은 전부 같은
서버 분기를 타는 이름들뿐이라, 앱은 자기 콜의 라벨을 자기가 잘못 붙일 수 있을 뿐
서버 동작을 바꾸거나 콜을 죽일 수는 없다. 2026-07-28 사고는 allowlist **밖** 값이
`create_call` 을 죽인 것이었고 그 경로는 닫혀 있다.

## 등록 API — JavaScript core

```ts
export function registerClientLayer(layer: { name: string; version: string }): void;
```

- **모듈 로드 시점에 호출한다. per-call 옵션이 아니다.**
- core 는 자기 자신을 `js-sdk/<core version>` 으로 자동 등록한다.
- 반환값 없음. throw 없음.

core 를 쓰지 않는 구현(flutter · python · cli · react-native native)은 등록 API 를
노출할 필요가 없다. 자기 레이어 하나를 같은 문법으로 직렬화해 보내면 된다.

## 처리 순서

6 개 구현이 반드시 이 순서로 처리한다. 순서가 다르면 같은 입력에서 다른 헤더가
나온다.

1. **검증** — 문법을 어기는 레이어를 버린다
2. **중복 제거** — 같은 `name` 은 먼저 등록된 것만 남긴다
3. **역순 정렬** — 바깥 레이어가 앞으로 온다
4. **개수 상한** — 8 개를 넘으면 앞에서부터 버린다
5. **길이 상한** — 256 바이트를 넘으면 맞을 때까지 앞에서부터 버린다
6. 남은 게 없으면 헤더를 보내지 않는다

## 구현 함정

- **Python 의 `$` 는 문자열 끝의 개행 하나를 허용한다.** `re.match(r"...$", "1.2.0\n")`
  이 통과한다. `re.fullmatch` 또는 `\Z` 를 써야 한다. JavaScript · Dart 의 `$` 는
  그렇지 않다. 이 명세를 처음 검증할 때 실제로 걸린 함정이다.
- 길이 상한은 **바이트** 기준이다. 유효한 레이어는 전부 ASCII 라 문자 수와
  같지만, 검사 자체는 바이트로 한다.
- 개수 상한과 길이 상한은 **역순 정렬 뒤에** 적용한다. 정렬 전에 자르면 안쪽
  레이어가 사라진다.

## conformance vector

`conformance/x-vox-client.vectors.json` 이 SoT 다. 6 개 구현이 전부 같은 벡터로
테스트한다.

다른 레포는 이 파일을 복사해 쓰되 **복사본을 단독으로 수정하지 않는다.** 문법이
바뀌면 벡터의 `version` 을 올리고 전 레포 복사본을 함께 갱신한다.

벡터의 `register` 는 **등록 순서**(안쪽부터)이고 `header` 는 기대 직렬화 결과다.
`header` 가 `null` 이면 헤더를 보내지 않아야 한다는 뜻이다.
